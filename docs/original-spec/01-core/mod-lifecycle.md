## Behavior detail

1. (both) `StorageMod` constructor runs at mod construction. Registers on the mod event bus: `setup` (FMLCommonSetupEvent), `doClientStuff` (FMLClientSetupEvent, client only), `registerCapabilities` (RegisterCapabilitiesEvent), `enqueueIMC` (InterModEnqueueEvent). If running on the client dist, calls `StorageModClient.preInit(mc, bus)` immediately (keybind registration, model baking, screen registration, render pipelines, GUI overlays, client extensions, config-screen factory). Registers `Config.commonSpec` (COMMON type) and `Config.serverSpec` (SERVER type) as mod configs, and registers `Config` and `NetworkHandler` classes as bus subscribers. Calls `Content.init()` (currently an empty method — all registration happens in `Content` static initializers, i.e. at class-load). Calls `Platform.register(bus)` which attaches all `DeferredRegister` handles to the bus. Sets static `StorageMod.polymorph = ModList.get().isLoaded("polymorph")` (inferred: the flag is only consumed by a commented-out line, see `CORE-08`).
2. (both) `setup`: logs "Tom's Storage Setup starting"; registers `VanillaMultiblockInventories::checkChest` into `MultiblockInventoryAPI.EVENT`; if `sophisticatedstorage` is loaded, registers `SophisticatedDoubleBlocks` (both NF; the SH `MultiblockInventoryAPI` is documented in `util-api.md`).
3. (client) `doClientStuff`: calls `StorageModClient.clientSetup()` which registers `StorageModClient.class` on the game (NeoForge) event bus, enabling `ItemTooltipEvent` (extra tooltips via `ClientUtil.collectExtraTooltips`), `SubmitCustomGeometryEvent` (terminal outline + configurator outline), and `ClientTickEvent.Post` (keybind handling). The line `if (polymorph) PolymorphTerminalWidget.register();` is commented out — *dead code* on NF (see `CORE-08`).
4. (both) `registerCapabilities` (NF): registers block item capabilities for 5 block entity types: `open_crate` and `filing_cabinet` expose a `VanillaContainerWrapper` over the BE's container; `inventory_connector`, `inventory_interface` and `inv_proxy` expose `PlatformItemHandler` (the IProxy delegating handler, see `inventory-access.md`).
5. (both) `enqueueIMC`: if `theoneprobe` is loaded, sends IMC message `getTheOneProbe` to it whose payload lazily instantiates `com.tom.storagemod.top.TheOneProbeHandler` by reflection (class name string); on failure logs a warning and returns null.
6. (both) `Content` registration helpers: `blockWithItem(name, ...)` registers the block and an item of the same name (item display name uses the block's description prefix via `useBlockDescriptionPrefix()`); `item(name, ...)` additionally adds the item to the creative tab list; `blockEntity(name, factory, blocks...)` registers a `BlockEntityType` bound to the given blocks; `menu(name, supplier)` registers a `MenuType` with `FeatureFlags.VANILLA_SET`. Block properties: `wooden(p)` = wood map color + wood sound + hardness 3.0; `filing_cabinet` gets stone map color + stone sound + hardness 3.0 instead. All block items are `BlockItemTSS` (SH block item subclass, 02-storage/06-client-ui territory) except `painted_trim`, `inventory_cable_framed`, `inventory_proxy` and `inventory_cable_connector_framed`, which use `PaintedBlockItem` (06-client-ui territory).
7. (both) `StorageTags` defines 4 block tag keys (all namespace `toms_storage`): `remote_activate` (blocks activatable by wireless items — contains `storage_terminal` and `crafting_terminal` per the shipped tag file), `trims`, `inventory_connector_skip`, `inventory_configurator_skip`.
8. (server) `ServerEvents.onBlockBreak` (LOW priority): when any block breaks, if its block entity has the `block_filter` attachment, the attached filter's contents are dropped at the block position. (This is how a filter item is returned when its host block breaks.)
9. (server) `ServerEvents.onLeftClick` (LOW priority): on left-click of a block, if the level is server side and the main-hand item implements `ILeftClickListener` (SH item interface, 02-storage), its `onLeftClick(stack, pos, player)` is called; if it returns true the event is canceled (block breaking suppressed).
10. (client) `StorageModClient.preInit` (NF): registers listeners for keybinds, model baking, screens, render pipelines, GUI overlays, client extensions; registers `IConfigScreenFactory` extension (`ConfigurationScreen` — the vanilla-style mod config screen).
11. (client) `initKeybinds`: creates `KeyMapping` with lang key `key.toms_storage.open_terminal` ("[Tom's Simple Storage] Open Terminal"), context IN_GAME, default key `B` (GLFW keysym B), category GAMEPLAY.
12. (client) `clientTick` (ClientTickEvent.Post): if the player exists and the keybind was pressed this tick, sends `NetworkHandler.openTerminal()` (see `network.md`).
13. (client) `registerScreens`: binds 8 menu types to screens: `storage_terminal`→`StorageTerminalScreen`, `crafting_terminal`→`CraftingTerminalScreen`, `level_emitter`→`LevelEmitterScreen`, `inventory_link`→`InventoryLinkScreen`, `item_filter`→`ItemFilterScreen`, `tag_item_filter`→`TagItemFilterScreen`, `inventory_configurator`→`InventoryConfiguratorScreen`, `filing_cabinet`→`FilingCabinetScreen` (screens are 06-client-ui territory).
14. (client) `bakeModels`: for each possible state of `painted_trim`, `inventory_cable_framed`, `inventory_proxy`, `inventory_cable_connector_framed`, wraps the baked model in `BakedPaintedModel` (paint tinting, 06-client-ui).
15. (client) `registerOverlays`: registers GUI overlay `toms_storage:configurator_info` above all other layers, rendered by `ClientUtil.drawConfiguratorOverlay`.
16. (client) `registerPipelines`: initializes `CustomRenderTypes.linesNoDepth()` and registers the collected pipelines; if `iris` is loaded, assigns the lines pipeline to the IRIS `LINES` shader key (iris is an NF client-only dependency, *inferred* behavior).
17. (client) `renderWorldOutline`: draws a wireframe outline of the block the player is looking at when holding a wireless terminal (`WirelessTerminalItem.isPlayerHolding`) and the target is in `remote_activate` (see 04-wireless), plus configurator selection outlines.
18. (client) `registerClientExtensions`: registers `PaintedExtension` (model layer extension for painted blocks, 06-client-ui) for `painted_trim`, `inv_cable_framed`, `inv_proxy`, `inv_cable_connector_framed`.
19. (both) `Platform` statics (NF): `vivecraft` = mod `vivecraft` loaded (used for VR raytracing in `ClientUtil`); `curios` = mod `curios` loaded (used by `checkExtraSlots`); `checkUse(worldIn, hit, player, hand)` posts a synthetic `PlayerInteractEvent.RightClickBlock` and returns the cancellation result if canceled, else null (caller then falls through to `state.useWithoutItem`); `checkExtraSlots` looks up Curios inventory for the first stack matching a predicate; `notifyBlocks` posts the neighbor-notify cancel check via `EventHooks.onNeighborNotify`; `makeRegByteBuf` wraps a Netty buffer in a `RegistryFriendlyByteBuf` with `ConnectionType.NEOFORGE`; `getIngredientItems` returns ingredient item holders (custom ingredients via `items()`, tag ingredients via `getValues()`); `getCloneItemStack` delegates to `BlockState.getCloneItemStack`; `canScrapeWithItem` checks the `AXE_SCRAPE` item ability; `runWithPacketContext` is a no-op passthrough on NF (Fabric runs the runnable inside the packet context, see Fabric note below).

## Loader differences (Fabric)

- `Fabric/StorageMod` (entry) registers the same content via Fabric registries; `MultiblockInventoryAPI.EVENT.register(VanillaMultiblockInventories::checkChest)` is identical. Fabric config is a shedaniel autoconfig class (`Config implements ConfigData`) instead of `ModConfigSpec` (see `config.md`). Fabric registration is eager: `GameObject.get()` returns the value set during `runRegistration()` (no deferred holders) — *inferred* to be called from the mod initializer.
- `Fabric/Platform`: `STORAGE_MOD_TAB` is a `FabricCreativeModeTab` registered directly into `BuiltInRegistries.CREATIVE_MODE_TAB` in a static block; no attachment types on Fabric (the `block_filter` attachment is an NF-only mechanism — on Fabric the block filter lives on the block entity directly, *inferred*); `checkUse` uses the `UseBlockCallback` event instead of posting a synthetic event (returns the result, or null on PASS); `checkExtraSlots` uses the **trinkets** mod (`TrinketsApi.getAttachment(...).equipped(is, false)`) instead of Curios; `notifyBlocks` always returns true (Fabric has no cancelable neighbor notify — *inferred*); `canScrapeWithItem` checks `ItemTags.AXES` instead of the `AXE_SCRAPE` ability; `runWithPacketContext` wraps the runnable in `PacketContext.runWithContext` (Fabric requires packet context to be set when sending packets from non-tick code — this is why `TerminalSyncManager` calls it, see `terminal-sync.md`).
- `Fabric/PlatformItem` does not override `onItemUseFirst`; the equivalent hook is a `UseItemCallback` in `Fabric/StorageMod` (line ~147) that calls `PlatformItem.onRightClick`. `Fabric/PlatformBlockEntity` additionally implements `TickerUtil.OnLoadListener` with an empty `onLoad()` and a no-op `markCapsInvalid()`.
- `Fabric/GameObject`: `GameRegistry` collects objects and registers them eagerly in `runRegistration()`; `GameRegistryBE` uses `FabricBlockEntityTypeBuilder`; `GameObjectBlockEntity.addBlocks(...)` allows appending blocks after registration (NF has no equivalent).

## Behavior detail

### Server → client (inventory sync)

1. (server) `update(changeID, items, player, extraSync)`: if `changeID != lastChangeID` (SH TerminalSyncManager.java:116-126) (the BE bumps `changeCount` whenever the tracked inventory changes): set `lastChangeID`, then under `Platform.runWithPacketContext(player, ...)` run `updateInternal`. Independently, if `extraSync != null`, build an empty `CompoundTag`, let the callback fill it, and send it to the player as a separate `DataPacket` (this is how extra fields like sort/modes/searchType ride the same channel).
2. (server) `updateInternal`: compute the changed set (SH TerminalSyncManager.java:128-174) — for every (stack, count) in the new `items` map, remove it from the local `items` mirror; if it was absent or details differ (`equalDetails`), add the new count to `toWrite`; then every remaining entry in the mirror is written as a quantity-0 tombstone (removed item); replace the mirror with the new map. If `toWrite` is empty, nothing is sent (the `extraSync` packet in step 1 may still go out).
3. (server) For each stack in `toWrite`: `write(buf, stack)` — flags byte (bit 0 if quantity 0) (SH TerminalSyncManager.java:50-72), varint id (assigned via `idMap.computeIfAbsent`, id = `lastId++`, also recorded in `idMap2`), full stack encoding unless the id was already known (bit 2), then varlong quantity + varint used-slot-count when quantity != 0 (SH TerminalSyncManager.java:69-70). On `IndexOutOfBoundsException` (SH TerminalSyncManager.java:149-151; writeMiniStack 74-86) (stack larger than the buffer headroom), rewind and `writeMiniStack` instead: a placeholder stack (same item, empty NBT) with red lore `tooltip.toms_storage.nbt_overflow` ("This item's tag is too big, the item may not show correctly in the terminal") and flag bit 1 set.
4. (server) After each write, if the buffer size would exceed 64000 bytes or more than 32000 stacks are pending (and at least 2 stacks are buffered): flush the buffer as a `DataPacket` compound (SH TerminalSyncManager.java:154-166) (`d` = bytes, `l` = count as short) and start a new buffer; if the stack that just overflowed is itself larger than 64000 bytes even as a mini stack, it is written again as a mini stack into the new buffer (a single oversized stack can therefore produce a >64000-byte packet on its own).
5. (server) After the loop, a final non-empty buffer is flushed the same way. (SH TerminalSyncManager.java:167-172)
6. (client) `receiveUpdate(registryAccess, tag)`: reads `d` (SH TerminalSyncManager.java:176-181; read 88-114, BARRIER 98-99) (byte buffer codec) and `l` (short, default 0); decodes exactly `l` stacks via `read`: flags byte, varint id; if bit 2 is unset, decode the full stack (mini stacks arrive as the placeholder item + lore); if bit 2 is set, look up `idMap2` — an unknown id becomes a `BARRIER` item with red lore `tooltip.toms_storage.item_sync_error` ("Item Stack Sync error"); quantity/used-slot-count read only when bit 0 is unset (else both 0); the stack is inserted into both id tables. Stacks with quantity 0 remove the entry from `itemList`; others add/replace it. Returns whether `d` was present (so the menu knows a sync arrived).
7. (client) `getAsList()`: current displayed stacks (SH TerminalSyncManager.java:237-239) (`itemList.values()`). `getAmount(stack)`: displayed quantity (SH TerminalSyncManager.java:245) of a stack (0 if unknown) — used by the screen for counts.

### Client → server (interactions)

8. (client) `sendInteract(stack, action, mod)`: builds the `a` wire format (SH TerminalSyncManager.java:196-208) (step, wire formats above; `mod` = a modifier key held, recorded as bit 0; a null stack sets bit 1 and writes no id/quantity) and sends it to the server as a `DataPacket`.
9. (server) `receiveInteract(tag, handler)`: reads `a`; (SH TerminalSyncManager.java:218-234) flags byte; if bit 1 set, stack = null; else varint id → `idMap2` lookup (null id → null stack), varlong quantity; reconstructs a `StoredItemStack` copy with the client-supplied quantity (the server menu re-validates, 03-terminal); invokes `handler.onInteract(stack, SlotAction, mod)`.
10. (server) `fillStackedContents` / `fillCraftingFiller`: (SH TerminalSyncManager.java:241,259) feed the manager's item mirror into `StackedItemContents` / `TerminalCraftingFiller` (recipe-book contents, 05-integration/03-terminal).

### IAutoFillTerminal / IDataReceiver

11. (both) `IAutoFillTerminal` (implemented by terminal menus): (SH IAutoFillTerminal.java:11-16) `sendMessage(CompoundTag)` (menu→screen extra sync), `getStoredItems()`, `isSmartSearch()`. Static `updateSearch` list of `ISearchHandler`s: JEI (`JEIHandler`), EMI (`EMIPlugin`) and REI (`REIPlugin`) each register one (05-integration). `hasSync()` = list non-empty (SH IAutoFillTerminal.java:18-20) (the terminal screen shows the search-type button only when a recipe viewer is present or smart search is active, 06-client-ui). `sync(searchString)` pushes the current search string to every registered handler (so the recipe viewer filters in sync with the terminal search box). `getHandlerName()/getHandlerNameOr(text)` joins handler names with `", "` for button tooltips (falls back to the given text when no handlers are registered).
12. (both) `IDataReceiver.receive(ValueInput)`: (SH IDataReceiver.java:6) the single entry point for `DataPacket` payloads (network.md). Server implementations are terminal menus; client implementations are terminal screens.

## Loader differences (Fabric)

Identical SH classes; on Fabric, `update` must run inside a packet context (step 1) because the send happens from a packet handler, and `makeRegByteBuf` uses the two-arg `RegistryFriendlyByteBuf`.

## Behavior detail

### The One Probe (`TheOneProbeHandler`, NeoForge only)

1. **(both, init)** `StorageMod.enqueueIMC(InterModEnqueueEvent)` (NF/StorageMod.java:80-81; UNVERIFIED: the method exists only in the NeoForge `StorageMod`, a grep of Fabric/.../StorageMod.java finds no `theoneprobe` reference): when TOP is loaded, `InterModComms.sendTo("theoneprobe", "getTheOneProbe", ...)` with a supplier that reflectively instantiates `TheOneProbeHandler` (reflection keeps the compile-time dependency one-directional); on any `Throwable` it logs `"Failed to init TheOneProbeHandler"` and returns `null`.
2. **(server→TOP)** TOP invokes `apply(ITheOneProbe)`: stores the probe in the static `theOneProbeImp` and calls `theOneProbeImp.registerProvider(this)` (TheOneProbeHandler.java:38-41).
3. **(client)** `addProbeInfo(mode, probeInfo, player, world, blockState, data)` — three independent checks on the probed block entity `te = world.getBlockEntity(data.getPos())`:
   1. (TheOneProbeHandler.java:47-52) If `te` is an `InventoryConnectorBlockEntity`: add `tooltip.toms_storage.connector_info.size` (free, all), a progress bar `(all − free) / all` with filled color `0xFF8e691d` / alternate `0xFF342f26` and hidden text, and `tooltip.toms_storage.connector_info.inv` (blocks). Note the progress is called with total `usage.all()`, which can be `0` (`INT-07`).
   2. (TheOneProbeHandler.java:53-61) If `te` is a `BasicInventoryHopperBlockEntity`: if the hopper filter is non-empty, `addFilterInfo(...)`; if the hopper is redstone-disabled, add `tooltip.toms_storage.disabled_by_redstone`.
   3. (TheOneProbeHandler.java:62-74) If `te != null` and `te.hasData(Platform.BLOCK_FILTER)`: add `tooltip.toms_storage.block_filter` (header), then either `tooltip.toms_storage.block_filter.skip` or `tooltip.toms_storage.priority_<name>` (lower-cased `Priority.name()`), and — unless skipping and the filter slot is non-empty — `addFilterInfo(...)` for the filter item. Because connectors and hoppers also carry `BLOCK_FILTER`, their readout includes this block-filter section in addition to their own (observed from code; not separately verified in-game).
   4. `addFilterInfo` (TheOneProbeHandler.java:77-85): while the player sneaks (`isSecondaryUseActive`): a horizontal sub-panel (`LayoutStyle` border `0xFFFF0000`, spacing `2`) containing the item and its full vertical tooltip lines; otherwise a single line `tooltip.toms_storage.block_filter.item` with the item's hover name.

### Polymorph

1. **(both, init)** `StorageMod.polymorph` is set from `ModList.get().isLoaded("polymorph")` (NF) (NF/StorageMod.java:56) / `FabricLoader.getInstance().isModLoaded("polymorph")` (FB) (Fabric/.../StorageMod.java:169).
2. **(server)** `PolymorphHelper.getRecipe(pl, crafting, input, level)` → `PolymorphApi.getInstance().getRecipeManager().getPlayerRecipe(pl.containerMenu, crafting, input, level, pl)` — used by the crafting terminal block entity (area `03-terminal`) to resolve the player's recipe-book state; returns `Optional<RecipeHolder<CraftingRecipe>>` (PolymorphHelper.java:16-17).
3. **(client)** `PolymorphTerminalWidget` extends Polymorph's `PlayerRecipesWidget`, bound to `containerScreen.getMenu().getCraftingResultSlot()`:
   - `initChildWidgets`: sends an inventory-button click (button ID `1`) to the menu before super (PolymorphTerminalWidget.java:31-34) — this is the "fill grid from selected recipe" trigger (the button handler lives in `CraftingTerminalMenu`, area `03-terminal`).
   - `selectRecipe`: calls super, then the recipe-fetch + button-click body is **commented out** (dead) (PolymorphTerminalWidget.java:22-28).
   - `render`: `resetWidgetOffsets()` then super (widget re-positions itself relative to the result slot each frame) (PolymorphTerminalWidget.java:37-42).
   - `register()`: `PolymorphWidgets.getInstance().registerWidget(screen -> screen instanceof CraftingTerminalScreen ? new PolymorphTerminalWidget(s) : null)` (PolymorphTerminalWidget.java:44-52) — but the only registration calls are commented out: NF `StorageMod.java:69` (verified) and FB `StorageModClient.java:154` (not re-checked) (`INT-08`).
4. Both loaders additionally exclude `PolymorphTerminalWidget.java` from compilation unconditionally (block-comment excludes in the build scripts) (NeoForge/build.gradle:137; Fabric/build.gradle:130), so even an uncommented registration would not compile by default (`INT-08`).

### Sophisticated Storage (`SophisticatedDoubleBlocks`)

1. **(server, init)** `register()` adds `checkGroup` to `MultiblockInventoryAPI.EVENT` (SophisticatedDoubleBlocks.java:13-15). Called from NF common setup only when `ModList.get().isLoaded("sophisticatedstorage")` (`NF/StorageMod.java:62-64`, verified); the FB call is commented out (`FB/StorageMod.java:178-181`) and the class is unconditionally excluded from the FB build (`Fabric/build.gradle:131`, verified) — `INT-09`.
2. **(server)** `checkGroup(level, pos, state, extra)`: for every position in `StoragePositionGroups.getGroup(level, pos).memberPositions()` that is not `pos` itself, `extra.accept(pos)` (SophisticatedDoubleBlocks.java:17-22) — so a cable network counting inventories sees all parts of a multi-block storage.

### Multiblock inventory API (`MultiblockInventoryAPI`, `EventHandler`)

1. `MultiblockInventoryAPI.EVENT` is a static `EventHandler<MultiblockDetector>`; the invoker factory builds a single lambda that calls each registered `MultiblockDetector.detectMultiblocks(level, pos, state, extra)` in registration order (MultiblockInventoryAPI.java:10-19).
2. `EventHandler<T>`: a generic listener list. `register(listener)` is synchronized on an internal lock and appends + rebuilds the cached `invoker` via `invokerFactory` (EventHandler.java:23-35) (a composite lambda over the listener array); `invoker()` returns the cached invoker from an **unsynchronized** field read (EventHandler.java:37-39) (fine for single-threaded init; inferred safe).
3. Consumers: the inventory-cable network queries `EVENT.invoker()` when aggregating inventories to discover extra positions of multi-block storage (area `02-storage`).
4. `VanillaMultiblockInventories.checkChest(level, p, state, extra)`: registered on both loaders (NF `StorageMod.java:61`, FB `StorageMod.java:176`) (VanillaMultiblockInventories.java:13-27). If the block is a chest and `type != SINGLE`: `opos = p.relative(ChestBlock.getConnectedDirection(state))`; if the block at `opos` is the same block, is itself a non-`SINGLE` chest, has a *different* chest type (i.e. the two halves of one double chest), and the same `FACING` → `extra.accept(opos)`. (The different-type check is how the code distinguishes "the other half of this chest" from an adjacent independent double chest.)

### `ServerEvents` (NeoForge compat handlers)

1. `BreakBlockEvent` (priority `LOW`) (ServerEvents.java:19-25): if the broken block's entity `hasData(Platform.BLOCK_FILTER)`, the block-filter attachment's contents are dropped at the break position (the filter item is not lost when a configured block is broken).
2. `LeftClickBlock` (priority `LOW`) (ServerEvents.java:27-35): if the player's main-hand item implements `ILeftClickListener` and `onLeftClick(player, hand)` (UNVERIFIED: the call is `onLeftClick(stack, pos, player)` and the handler returns early on the client side, ServerEvents.java:29, :32) returns true, the event is canceled (used by filter/configurator items — areas `02-storage`/`03-terminal`).

### Fabric ModMenu (`ModMenu`)

1. Implements `ModMenuApi`; provides the AutoConfig client-config screen for the mod (ModMenu.java:8-13) (Fabric only; the NeoForge equivalent is the Cloth config screen factory in `NF/StorageModClient.java`, area `06-client-ui`).
